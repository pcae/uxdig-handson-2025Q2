# Consensus overview for This Project

This document is a agreement overview for This Project.  
We have compiled information and tips for development.  
If you have any questions, please contact me via Slack.

## 1. TypeScript

- TypeScript version is v4.8.2.
- TypeScript settings files is the following file:
  - `tsconfig.json`
- Strict application of types:  
  All variables, function arguments, and return values must be of an unambiguous type.
  If an exception occurs, please cite a clear reason for the exception and obtain approval.
- Use of type inference  
  In cases where types are obvious, TypeScript's type inference can be used to keep code concise.However, for complex logic, explicit type annotations are recommended.
- Define and use custom types:  
  Define interfaces and type aliases as needed to maintain consistent data structures throughout your code.
- Type Reuse and Extension: Reuse existing types and extend them as needed:  
  Avoid code duplication and improve maintainability by reusing and extending existing types as needed.
- Strict handling of type errors:  
  Type errors that occur at compile time should be resolved appropriately and not ignored. This greatly reduces the likelihood of run-time errors.

## 2. Immutable

Follow the below items to build a consistent, predictable, and maintainable code base.

- Adherence to the Principle of Immutability:  
  All coding must adhere to the principle of immutability. Do not directly modify data or objects, but create and manipulate new instances.

- Minimize side effects:  
  Minimize side effects and improve code predictability by not directly modifying the original data structure.

- Procedures for data modification:  
  When data changes are necessary, duplicate the original data and make changes to that copy. This maintains program stability and ease of debugging.

- Increased stability and maintainability:  
  Immutable coding improves program stability and maintainability, contributing to long-term project success.

- Balance with readability:  
  It is not recommended that too much emphasis be placed on immutability to the detriment of readability. In such cases, changes may be made at the discretion of the worker.

## 3. Orval

- [Orval](https://orval.dev/) is a tool for generating API calls based on an OpenAPI specification.
- Orval generates a client, a schema and a type for each API endpoint.
- Generating command is `pnpm generated:api`.
- If there have been updated OpenAPI specification, overwrite the updated file in `shared/api/resources` and run `pnpm generated:api` to updated mock server and client.
  - This command is not executed in CI/CD, so we must always commit locally generated files.
  - Run this command, the "example" defined in OpenAPI will also be output in JSON format under `src/api/generated/examples`.
- Generated files in the following directories:
  - `src/api/generated`
- Orval settings files is the following file:
  - `orval.config.ts`

## 5. State Management

The following two tools are used for state management.

- [Tanstack Query](https://tanstack.com/query/v4)
- [Jotai](https://jotai.org/)

Reasons for adopting the two tools and the differences in their roles

- Tanstack Query is primarily used to manage the state of data retrieved from the API.
- Jotai is primarily used to manage the status of data used only locally.

### 5.1. Tanstack Query

- [Tanstack Query](https://tanstack.com/query/v4) is an asynchronous state management tool for TS/JS.
- Tanstack Query version is v4.x
- Use the client and a type generated by Orval.
- In our modular monolith architecture, each module has its own query hooks in the `modules/[module-name]/hooks` directory.
- Shared queries can be placed in `shared/hooks` when needed across multiple modules.

### 5.2. Jotai

- [Jotai](https://jotai.org/) is a tool for state management.
- Jotai version is v2.x.
- State files are located in the following directories:
  - Module-specific state: `modules/[module-name]/stores`
  - Shared state: `shared/stores` (when needed across multiple modules)

### 5.3. Module Interface

- Each module exports its state management hooks and components through its public interface in `modules/[module-name]/index.ts`.
- Other modules should only access these exported hooks and components, not directly access the internal implementation.

## 12. Modular Monolith Architecture

This project adopts a modular monolith architecture. Please follow the rules below during development.

### 12.1. Module Structure

- Create independent modules for each business domain or functional unit
- Modules are placed in the `src/modules` directory
- Each module has the following structure:
  ```
  modules/[module-name]/
  ├── api/              # Module-specific API clients and server-side processing
  ├── components/       # Module-specific components
  ├── hooks/            # Module-specific hooks
  ├── stores/           # Module-specific state management
  ├── utils/            # Module-specific utilities
  ├── types.ts          # Module internal type definitions
  └── index.ts          # Module public interface
  ```

### 12.2. Module Dependencies

- Dependencies between modules must only be through explicit interfaces
- Each module's `index.ts` defines the public API, and other modules should only use this interface
- Implementation details within a module should not be exposed externally
- Dependencies should be unidirectional only to avoid circular dependencies

### 12.3. Shared Resources

- Code shared across multiple modules is placed in the `src/shared` directory
- Shared resources are categorized as follows:
  - `shared/components`: Common UI components
  - `shared/ui`: Basic UI components (e.g., shadcn/ui)
  - `shared/hooks`: Common hooks
  - `shared/utils`: Common utilities
  - `shared/types`: Common type definitions

### 12.4. Module Development Guidelines

- **Independence**: Each module should be developed, tested, and deployed independently as much as possible
- **Encapsulation**: Implementation details within a module should not leak externally
- **Clear Boundaries**: Define clear responsibilities and boundaries for each module
- **Public Interface**: Keep the API exposed to other modules minimal and explicitly defined
- **Testing**: Create unit tests for each module and test at module boundaries

### 12.5. Naming Conventions

- Module names should use nouns representing functionality or domains, written in camelCase
  - Examples: `auth`, `userManagement`, `notifications`
- Public interface naming should be clear and consistent
  - Examples: Components: `Login`, Hooks: `useAuth`, Functions: `validateUser`

### 12.6. Integration with App Router

- Next.js App Router page components should use components and hooks exported from modules
- If page-specific logic is needed, place it in the appropriate module or consider creating a new module
